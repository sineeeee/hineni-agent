# 逐项配置：含义、处理流程与更新方式

本文件与网页共用 config/guide.ts、learning.ts、processing-guide.ts，由 npm run docs 生成。规则来自当前实现。网页显示实际安装目录和数组序号；本文的 n、m、用途、名称是需要替换的路径位置。参数默认值不是你现在保存的值。

公共设施和公共默认值在根 config.yaml；个人设置写 agents/<id>/config.yaml，模型 Key 写同目录 .env，Bot Token 与管理令牌写根 .env。详见 agent-layout.md。配置保存并重启后用于新运行。参数是规则，不随聊天自行变化；程序更新的状态、索引、摘要会在各流程中说明。

## server

启动时创建 API 和管理页面监听。修改端口后需要打开新地址；改变管理口令后需要重新登录。

适用范围：全局；保存配置并重启服务。

### 网页和接口允许从哪里访问等参数的处理流程

1. 启动时读取 server，创建 API 和管理网页两个监听地址。每个请求读取 Bearer 口令，与启动时从环境变量取得的口令比较。
2. 保存配置只更新文件和管理端草稿值；重建服务后新监听地址和新口令才接管请求。

实现位置：`src/admin/server.ts · servers`；`src/application.ts · startManaged`。

### 网页和接口允许从哪里访问 · host

保存位置：根 config.yaml → `server.host`。默认：`"127.0.0.1"`。

**含义。** 127.0.0.1 表示只允许这台电脑访问；监听其他地址才可能从别的电脑连接。

**调整结果。** 这会改变网络访问范围，不影响聊天性格或模型。对外开放时需要设置好访问保护。

**具体影响。** 绑定的网络地址。127.0.0.1 仅本机可访问；对外监听需自行部署访问保护。

**处理过程。** 见本组“网页和接口允许从哪里访问等参数的处理流程”，该参数在上述具体步骤使用。

**更新与下一轮。** 启动服务时读取。程序不会自己修改这些值；改变端口后要打开新地址。

### 管理口令存在哪个变量里 · tokenEnv

## model

主模型负责聊天、工具循环和历史压缩；fast 是五类辅助 JSON 调用的默认模型；embedding 只产生记忆向量。模型列表由接口地址和对应 key 获取，不代表列表中所有模型都支持当前任务。

适用范围：全局默认，可在 agent 的 main 或 models 覆盖；保存并重启。

以下默认值以 main 为例。fast 默认 gpt-4.1-mini/maxOutput 2000；embedding 默认 text-embedding-3-small/maxOutput 1；query、maintenance、emotion、rerank 默认继承 fast。网页按具体用途显示。

### 请求协议等参数的处理流程

1. 先由 agentConfig 合并该 agent 的有效模型配置。主模型交给 PiExecutor；query、maintenance、emotion、rerank、spark 分别把自己的字段覆盖在 fast 上；embedding 单独使用向量模型。
2. 每个模型槽位通过 protocol 选择 Responses 或 Chat Completions。主模型由 Pi 转换工具和消息；辅助模型发送用途指令与本次材料，要求 JSON；摘要沿用主模型协议，向量模型始终走 embeddings。Responses 设置 store:false，每次完整传入编排材料，不接远端会话。列表读取是独立 /models 请求，不会验证模型是否支持全部功能。
3. 模型设置不由运行结果回写。辅助结果由记忆或心情模块接收，影响本轮回忆或下一轮状态。

实现位置：`src/config/schema.ts · agentConfig`；`src/shared/models.ts · OpenAIModels.model / json / embed`；`src/layer4/pi.ts · PiExecutor`。

### 请求协议 · protocol

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `models.<用途>.protocol`。默认：`"responses"`。

**含义。** 默认 responses，向 /responses 发请求；chat-completions 向 /chat/completions 发请求。

**调整结果。** 主模型、历史压缩和辅助 JSON 请求按各自模型槽位选择协议；向量仍走 /embeddings。保存并重启生效。新模型建议用 Responses，仅支持旧接口的服务可选 Chat。不会启用远端会话或改变人格。

**具体影响。** responses（默认）或 chat-completions。主调用和辅助调用各自使用槽位协议；压缩沿用主模型。Responses 使用 store:false，不使用远端会话 ID。向量忽略此项。保存并重启生效。

**处理过程。** 见本组“请求协议等参数的处理流程”，该参数在上述具体步骤使用。

**更新与下一轮。** 下一轮按这里选择的模型发请求。配置本身不会随聊天变化；已开始的工作仍使用开始时的设置。

### 一次最多生成多少内容 · maxOutput

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `models.<用途>.maxOutput`。默认：`8192`。

**含义。** 给主模型或辅助模型的输出长度上限，单位 token。

**调整结果。** 太小可能让回答或辅助判断写不完；更大只是允许写长，不强迫长篇回答。历史摘要另看 history.summaryTokens，向量模型不使用此项。

**具体影响。** 主模型或辅助 JSON 调用的总输出 token 上限，推理可能占用其中一部分。历史摘要请求取 main.maxOutput 与 history.summaryTokens 较大值；摘要实际保留文字仍受 summaryTokens 限制。embedding 忽略此项。

### 模型的思考强度 · reasoning

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `models.<用途>.reasoning`。默认：`"off"`。

**含义。** 主对话、历史压缩和辅助模型分别使用所属模型卡片的设置；辅助用途缺省继承 fast。

**调整结果。** low 等档位在 Responses 中发送 reasoning.effort，在 Chat 中发送 reasoning_effort。更高可能更慢、费用更高。辅助请求与压缩设置 off 时不附加推理参数，服务端可能仍默认开启思考；不支持推理参数的模型应选 off。保存并重启后生效。

**具体影响。** 主对话和摘要使用 main 的推理强度；辅助请求使用各用途覆盖或 fast 的推理强度。辅助与摘要的 off 不发送参数，遵循服务端默认；向量不使用此项。

### 特殊服务的兼容设置 · compat

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `models.<用途>.compat`。默认：`{}`。

**含义。** 当某个 OpenAI 兼容服务和标准接口有差别时，用这里调整 Pi 的请求。

**调整结果。** 第四层直连 api.deepseek.com 时默认 supportsDeveloperRole=false，让人格仍以 system 身份发送，避免 DeepSeek 把 developer 当普通用户文字；同时默认 supportsMidConvoSystemMessages=true，保留动态背景在历史之后。明确填写的值优先；其他地址保持 Pi 默认。代理需要按服务实际语义配置。辅助模型直接发送 system，不用此项。保存并重启生效。

**具体影响。** 第四层 Pi 的兼容键。直连 api.deepseek.com 自动默认 supportsDeveloperRole=false，保留 system 身份，并默认 supportsMidConvoSystemMessages=true 保留背景的位置；用户明确值优先，其他端点保持 Pi 默认。辅助调用直接发送 system，不使用此项。

## history

第二层从旧摘要检查点接上后续原文；工具结果只取尾部进入历史视图。超过阈值才调用 main 批量压缩较早部分。压缩不改原始 JSONL；新输入取消未交接回复时会删除对应原文。

适用范围：历史预算和 pollMs 均按当前 agent 生效。保存并重启。

### 历史多大时开始压缩等参数的处理流程

1. ContextBuilder.build 调用 History.view：从数据库的 history:<agent_id> 读取已压缩到哪个事件（through）和累计摘要（summary），再读取 through 之后的事件。投递确认和 run_finished 不加入这份历史。
2. History.render 保留事件时间、来源、发言人、正文和附件说明；旧工具结果只取末尾 toolTailTokens。估算“旧摘要＋剩余原文”的 token 数。
3. 超过 triggerTokens 时，从最新内容往前尽量留出 targetTokens−summaryTokens 的原文空间，其余较早事件分批交给 main 模型总结，输入同时包含旧摘要和最终摘要 token 预算；请求总输出额度取 summaryTokens 与 models.main.maxOutput 的较大值，避免推理先耗尽摘要额度。只接受完整 JSON 和未超过保留预算的摘要；不完整或超限不推进检查点。总结成功后把新的 through/summary 写回数据库；原始 JSONL 不改。
4. 最后把累计摘要和保留原文交给第三层，以摘要消息和原有user/assistant消息排列在动态背景之前。下一轮从新 through 接续，而不是再总结全部历史。

实现位置：`src/layer2/history.ts · History.render / view`；`src/shared/models.ts · OpenAIModels.summarize`；`src/layer3/context.ts · ContextBuilder.build`。

### 历史多大时开始压缩 · triggerTokens

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `history.triggerTokens`。默认：`600000`。

**含义。** 旧摘要加最近原文超过这个容量，才把较早部分重新总结。

**调整结果。** 例如 600000 改成 300000，会更早用摘要代替旧原文，费用和处理量可能减少，但旧细节更依赖主动查记录。不会删除原始聊天。

**具体影响。** 旧摘要加待保留原文的估算 token 超过此值才压缩。越大越多原文、成本更高；查看历史页不会触发压缩。

**处理过程。** 见本组“历史多大时开始压缩等参数的处理流程”，该参数在上述具体步骤使用。

**更新与下一轮。** 每次准备新一轮回复时使用。聊天记录不断追加；达到容量门槛才改写摘要。这里的容量规则不会自动变化。

### 压缩后尽量留下多少历史 · targetTokens

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `history.targetTokens`。默认：`350000`。

**含义。** 一次压缩结束后，希望“旧摘要＋近期原文”缩到的大致容量。

**调整结果。** 从 350000 改成 200000，会一次压掉更多较早内容，之后更久才碰到触发线；它必须小于开始压缩的门槛。

**具体影响。** 压缩时从末尾尽量保留原文，容量扣除 summaryTokens 后作为保留目标。必须低于 triggerTokens，不是每轮硬裁切。

**处理过程。** 见本组“历史多大时开始压缩等参数的处理流程”，该参数在上述具体步骤使用。

**更新与下一轮。** 每次准备新一轮回复时使用。聊天记录不断追加；达到容量门槛才改写摘要。这里的容量规则不会自动变化。

### 旧聊天摘要允许多长 · summaryTokens

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `history.summaryTokens`。默认：`12000`。

**含义。** 告诉总结模型，较早经历的累计摘要最多生成多少 token。

**调整结果。** 调大能容纳更多旧事和未完成事项，但摘要也会占用近期原文的空间；太小可能让总结不完整。这不是压缩前允许读取的长度。

**具体影响。** 滚动摘要最终保留的文字 token 上限。摘要请求的总输出额度取它与 models.main.maxOutput 的较大值，为推理和 JSON 留空间；输出仍须完整且文字不超此值，否则不推进压缩检查点。保留重要事件、修正、未完成事项和工具结果。

**处理过程。** 见本组“历史多大时开始压缩等参数的处理流程”，该参数在上述具体步骤使用。

**更新与下一轮。** 每次准备新一轮回复时使用。聊天记录不断追加；达到容量门槛才改写摘要。这里的容量规则不会自动变化。

### 回顾旧工具结果时保留多少 · toolTailTokens

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `history.toolTailTokens`。默认：`200`。

**含义。** 以后再次看聊天历史时，每条工具结果只带末尾这一段，避免长报错挤满上下文。

**调整结果。** 200 改成 400，主模型回顾时能看到更长的结尾。工具名和输入参数仍在历史中；完整结果仍可查文件。本轮刚执行完的工具另受 runtime.maxToolChars 限制。

**具体影响。** 历史视图仅保留工具结果末尾这些 token；工具名、参数仍在记录里，完整结果另存文件。不是当前工具循环的结果上限。

### 人格、记忆和状态的总空间等参数的处理流程

1. 每轮先获得第二层历史，再自动查找记忆、更新交流间隔并读取状态。开启context.spark时，每轮先按sparkProbability独立抽签；未抽中不发辅助请求。抽中后与记忆召回并行调用独立灵感模块：只给人格与本轮原始文字，不给旧聊天、回忆、状态或自动时钟。有效spark字符串按sparkTokens裁剪，通过个人prompt-mapping.yaml的text.spark模板，作为可忽略的本轮想象背景；不持久化、不自动执行，也不调整情绪。超时、异常或非字符串结果记录context警告并跳过；本轮被取消仍向上传播取消。基础 prompt＋persona 合计先取最多 4000 token；随后附加最多 5000 token 的 [Project]（目录、发送目标、Skills 清单）和 [Style]。
2. system 先按 layer3Tokens−stateTokens−200 预留空间裁切。另把回忆写入 [Recalled memories]，把状态写入 [Current state]，再按 layer3Tokens 减 system 实际长度裁切这份动态背景。这里裁的是文本，过小可能截断 JSON 的末尾。
3. 检查主模型容量：可用输入≈contextWindow−maxOutput−safetyTokens。如果 system、历史和动态背景仍超限，才要求第二层再压缩历史；图片另按每张 4096 token 预留。仍装不下就报错。
4. 初始顺序：system与人格/工具说明 → 历史摘要和原文 → system角色的本轮召回、角色自身状态与时间背景 → user角色的最新触发批次及附件。当前真人输入之前尚未获得成功文字回复的连续真人输入一起移到背景之后；不重复放在历史原文中。背景每轮替换，不写进历史；同批新消息只出现一次，图片预算再次压缩后仍按此顺序重建。
5. trace 开启时保存构建结果和 layer2 交接材料到 .runtime/traces/<run>.json；第四层还把每次主请求保存到 .runtime/requests/<run>/。不回写这些预算参数。

## memory

每轮：提炼查询 → 词法/向量召回 → 加权、重排、去重复 → 时间邻居和联想 → 按预算拼入背景。后台索引维护和主 agent 的记忆整理是两件事。

适用范围：每个 agent 独立设置维护频率与整理时间；保存到自己的 config.yaml，保存并重启。

### 聊天前自动回忆等参数的处理流程

1. MemoryService.recall 接收最近对话材料。需要时由 query 小模型产生 queries，程序把前 queryDirections 条合成一个搜索句；失败或超时使用原材料。
2. search 同步 memory.json 的文字内容，分别计算词语重叠和向量相似度，筛掉完全不相关条目，再结合长期强度、重要性、熟悉度、情绪和短期激活排序。可再用 rerank 小模型加分、降低重复摘要的排名。
3. recall 按 maxItems 选主回忆，再补时间邻居或一条突然联想；按 summaryTokens、detailsItems/detailsTokens 和 memoryTokens 装入结果；某条装不下则跳过该条，继续尝试后面的。ContextBuilder 把这些条目作为 [Recalled memories] 背景交给主模型，不要求它逐条说出来。
4. 自动想起可更新 state.json 的 activation 时间；真正聊起后的长期加深由 afterRun 另做。memory.json 原文不因一次召回被改写。

实现位置：`src/layer3/memory.ts · recall / search`；`src/layer3/context.ts · ContextBuilder.build`。

### 先让小模型想想该查什么等参数的处理流程

1. ContextBuilder 将本轮输入放在查询材料开头，预留约七成 queryInputTokens；近期用户话和内部触发补充指代背景，助手分句和工具不计入。
2. recall 以这份材料做缓存键。query 开启且缓存不可用时，把开头 queryInputTokens 个 token 交给 query 模型，system 使用 prompts.query 或默认“最多三条查找旧事的查询”。
3. 把返回 queries 的前 queryDirections 条追加到原始检索材料，一起进行关键词和向量检索；空数组仍使用原始材料检索。它们不是多次独立检索。成功结果只缓存在本进程，queryCacheSeconds 后失效。失败或超过 queryTimeoutMs 就用原材料。
4. search 再把查询开头最多 1000 token 交给 embedding，把结果用于语义比较；词法匹配也用查询文本。查询句本身不直接替换主模型历史，只有最终回忆进入 [Recalled memories]。

实现位置：`src/layer3/context.ts · ContextBuilder.build`；`src/layer3/memory.ts · recall / search`；`src/shared/models.ts · json / embed`。

### 搜索第一名比后面强多少等参数的处理流程

1. 先算文字匹配和语义匹配的两个名次：R=1/(rrfK+文字名次)+1/(rrfK+语义名次)，名次从 1 开始。
2. 计算最终基础分：R×(base + strength×A + importance×I + familiarity×F + emotion×E + activation×B)。A 是衰减后的长期强度；I=(importance−1)/4；F=1−exp(−重温次数/5)；B 是最近想起的短期热度；E 是与当前情绪匹配且随发生时间淡去的程度。
3. 按分数取 candidates，再重排和减少重复；最终只把选中的记忆放入上下文，不把这套权重直接念给主模型。参数不回写，实际分数每次搜索重新算。

实现位置：`src/layer3/memory.ts · search`。

### 顺带想起同一时期的几件事等参数的处理流程

1. 先按搜索排名取得主回忆，把第一条作为锚点。时间邻居按 occurred_at 与锚点相差的小时数筛选、从近到远排序；补入前 temporalNeighbors 条，挤掉末尾部分主回忆，尽量保持 maxItems 名额。
2. 每次自动召回把数据库 recallRound:<agent_id> 加一。抽中 associationProbability 且已有锚点时，从未入选的记忆里挑候选：与锚点有相同 people 项，或发生时间相差不足 24 小时；距离上次联想的轮数必须大于 associationCooldown。
3. 从符合条件的候选中随机选一条，在摘要前加“[突然联想]”，按 associationTokens 截短并清空 details。联想可比 maxItems 多一条，但仍受 summaryTokens 和整体 memoryTokens 限制，装不下会被跳过。
4. 数据库 associations:<agent_id> 记录已选联想的轮数，后续用于冷却检查；不是改写 memory.json 的内容。这只是交给主模型的背景，最终是否提起由它决定。

实现位置：`src/layer3/memory.ts · MemoryService.recall`；`src/layer2/store.ts · Store.get / set`。

### 普通记忆多久淡去一半等参数的处理流程

1. 每次搜索时，把记忆重要性转换为 I=(importance−1)/4，再算长期半衰期 H=baseHalfLifeDays×(1+importanceMultiplier×I)。长期强度 A=上次保存强度×2^(−距 strengthAt 的天数/H)。这里只算分，不删除 memory.json。
2. 自动回忆选中条目时，只在尚无标记时向 state.json.activation 写当前时间，已有标记不刷新；搜索时短期热度 B=2^(−距离激活的分钟数/activationHalfLifeMinutes)。超过 activationTtlHours 的标记在 state() 读取时清理。
3. 整轮后的 emotion 模型返回 memory_mentions，只有出现在本轮候选中的有效编号才算真正重温。afterRun 更新强度为 A+reinforcementGain×(1−A)，刷新 strengthAt、熟悉次数加一，并刷新 activation。
4. 长期强度和熟悉次数存 .runtime/search-index.json，短期标记存 state.json。下一轮重新计算排序，因而可能更容易想起。state.enabled=false 会跳过 afterRun；activationEnabled 只控制自动召回处的写入，不能完全禁用所有短期影响。

实现位置：`src/layer3/memory.ts · search / recall / afterRun / state`。

### 为每条记忆写一句查找线索等参数的处理流程

1. sync(false) 读 memory.json，按条目内容和向量模型签名检查变化，更新搜索用的文字副本。原文变化或向量模型变化会使相应旧描述/向量失效，但仅修改分片参数不会重做已有向量。
2. sync(true) 按 maintenanceBatchItems 分批、批内逐条处理缺少向量的记忆。searchDescription 开启且还没描述时，给 maintenance 模型完整条目，取 search_text 的前 descriptionTokens。
3. 把“检索描述＋原记忆文字”按 chunkTokens 和 chunkOverlap 切片，再调用 embedding；一批最多 20 个片段。单条受 maintenanceTimeoutMs 限制，成功结果写入 .runtime/search-index.json；失败记日志，保留 memory.json。
4. daily 由定时脚本调用；debounced 由后台每 pollSeconds 检查文件修改时间，静置超过 debounceSeconds 后调用。自带每日维护在 debounced 模式仍会执行。

### 允许模型主动查更多记忆等参数的处理流程

## state

读取状态时按时间回稳、清理过期念头；整轮第四层结束后调用 emotion 模型给出增量，程序限幅后写入 state.json。下一轮作为 Current state 背景。

适用范围：可按 agent 覆盖；不等待平台送达。保存并重启，已有状态不立即重置。

### 根据经历更新心情等参数的处理流程

1. MemoryService.state 先读 state.json，以 updated_at 到现在经过的时间补算消退。整体心情=baseline+(旧心情−baseline)×2^(−经过小时/moodHalfLifeHours)；各项短期情绪=旧值×2^(−经过分钟/emotionHalfLifeMinutes)。过期念头、关注点和激活标记在此清理。
2. 第四层启动后有文字、工具结果或主动沉默并结束，Runtime 才把这轮交给后台 afterRun；不等待发送成功。afterRun 给 emotion 模型的 user 材料包含 persona、policy、过滤后的state、本轮 input 和候选 memories；不传activation编号表和conversation_context路由数据。policy 明确 0–100 分制、允许情绪名称、启用驱动力、敏感度和限幅；评分提示词要求返回分数增量且不自行乘倍率。
3. 收到建议后：整体心情增量先乘 eventSensitivity，再限制到 ±moodDeltaLimit，累加后限制在 0–100。单项情绪和驱动力用各自倍率，限制到 ±dimensionDeltaLimit，再限制最终范围。返回 thoughts/focus 数组时替换当前列表；未返回时保留旧列表。
4. updateState 串行写 state.json。下一轮 ContextBuilder 读取它，每轮先读取个人prompts/prompt-mapping.yaml（缺字段用内置默认，列表整体替换），每轮按thoughtContextProbability和focusContextProbability分别抽一次，只决定现有候选是否呈现；未抽中不清除state。stateContext按映射挑自然描述；默认：心情按25/42/62/80分档；情绪至少1分、取最高两项，按15/40/70分档；驱动力偏离自己baseline至少5分才取最突出两项。裁到 stateTokens 后拼入 [Current state]，完整数字留在文件。assessed_at只在回合评分时更新，用来注明缘由的时间；updated_at仍是衰减计算时间。旧轮后台尚未完成时，新轮可能先读到旧状态。stateExpression 告诉主模型这是此前背景，当前输入可立即改变反应；closeness 是短时冲动而非关系评分。日志 mood 显示实际应用增量与被忽略名称，不记录本轮私密正文。单纯 GET state 会补算但不保证当场写文件；经过 updateState 才保存。

实现位置：`src/layer3/memory.ts · state / updateState / afterRun`；`src/layer2/runtime.ts · moodChains`；`src/layer3/context.ts · ContextBuilder.build`。

### 让模型知道距离上次说话多久等参数的处理流程

1. ContextBuilder 选定这一轮回复目标后，调用第二层 Store.gap；查询同一 agent、同一目标最近一条 agent_reply 文字块。
2. 计算当前时刻减那条记录的提交时间，返回 seconds_since_last_response、上次时间和 response_id；没有历史回复则间隔未知。不是按 Telegram 送达算，也不是一轮生成结束算。
3. 通过 MemoryService.updateState 写到 state.json.conversation_context。下一轮又重新计算；stateContext 将当轮间隔按1分钟/15分钟/2小时分档，写成自然时间距离和接话建议放到 [Current state]，同时保存在 trace.layer2 供检查。关闭 gap 会移除状态中的这个字段。

实现位置：`src/layer2/store.ts · Store.gap`；`src/layer3/context.ts · ContextBuilder.build`；`src/layer3/memory.ts · updateState`。

### 根据经历更新心情 · enabled

## style

所有风格项写进主模型 system 的 [Style]。这是表达指导，不是场景分类器或字数裁剪器；工作交付可以展开。

适用范围：可按 agent 覆盖；保存并重启。只有模型读到提示词后影响表达。

### 平时尽量说几句话等参数的处理流程

1. ContextBuilder 在每轮开始读取有效 style 配置，写成 system 中的 [Style] 段。开头说明日常通常一两句；句数、字数、段数和主动提旧事数量是软上限，不要求达到。复杂交付按需展开。
2. warmth、humor、directness、restraint、emotionExpression 小于 0.34 写“较少”，小于 0.67 写“适中”，其余写“较强”；其他字段使用数值或 true/false 写入。emotionExpression 和 restraint 还会按相同分界附上具体行为指导（轻轻带过/具体反应/明显流露，以及按场景收住感受）。这里没有另一次场景判断 API。
3. 主模型结合完整背景决定怎样表达。程序不根据这几个数字裁剪已生成回复，也不为口头禅或重复旧事维护严格计数；最终发送拆分另由第四层和 delivery 处理。

实现位置：`src/layer3/context.ts · ContextBuilder.build`；`src/config/style-prompt.ts · buildStylePrompt`；`src/config/help.ts · fieldHelp.style`。

## delivery

1. 第四层提交文字或发送工具动作后，第二层记入发送队列。Outbox 在入队时按 split 拆成 parts，串行取任务交给第一层；交接前可被同一聊天的新触发删除，交接后整条任务继续发送。

## scheduler

启动可编辑的定时子进程；默认脚本向第二层发 internal_event。新触发按同一打断逻辑处理，模型可选择沉默。重启重新抽随机时间，不补跑错过事件。

适用范围：每个 agent 有自己的 schedule.ts、schedule.once.json 和进程；一次性任务由宿主调度，到期仍提交同一事件入口；主目录是公共默认值。自定义脚本只有读取相应字段才受其影响。保存后可只重启自己的脚本。

### 启动自动提醒脚本等参数的处理流程

1. Scheduler 为每个启用的 agent 启动自己的脚本进程；读取其独立 config.yaml，安排自己的每日维护、做梦和随机机会。脚本带 agent_id 向同一个 /v1/events 提交事件。
2. 随机等待分钟数=min+Math.random()×(max−min)；到期按 timezone 算当前小时，只有 activeStart≤小时<activeEnd 才向 /v1/events 发 internal_event。然后重新抽下一段等待。
3. 内部事件带基础提示文字，进入第二层普通触发流程，再经过第三层和第四层；模型可选择沉默。参数不是每秒回写的状态；重启脚本会重新抽时间，不保存下次触发点或补跑错过事件。

## drives

## memory.rankWeights

每轮：提炼查询 → 词法/向量召回 → 加权、重排、去重复 → 时间邻居和联想 → 按预算拼入背景。后台索引维护和主 agent 的记忆整理是两件事。

适用范围：每个 agent 独立设置维护频率与整理时间；保存到自己的 config.yaml，保存并重启。

### 相关性本身的分量等参数的处理流程

1. 先算文字匹配和语义匹配的两个名次：R=1/(rrfK+文字名次)+1/(rrfK+语义名次)，名次从 1 开始。
2. 计算最终基础分：R×(base + strength×A + importance×I + familiarity×F + emotion×E + activation×B)。A 是衰减后的长期强度；I=(importance−1)/4；F=1−exp(−重温次数/5)；B 是最近想起的短期热度；E 是与当前情绪匹配且随发生时间淡去的程度。
3. 按分数取 candidates，再重排和减少重复；最终只把选中的记忆放入上下文，不把这套权重直接念给主模型。参数不回写，实际分数每次搜索重新算。

实现位置：`src/layer3/memory.ts · search`。

### 相关性本身的分量 · base

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `memory.rankWeights.base`。默认：`0.5`。

**含义。** 即使某条记忆不重要也不熟悉，只要与当前问题相关，仍保留一份基础优势。

**调整结果。** 调大后，重要性和心情等额外偏好相对弱一些；不改变搜索词。

**具体影响。** 相关性融合分的基础系数，即使其他记忆特征弱也保留相关性的贡献。

**处理过程。** 见本组“相关性本身的分量等参数的处理流程”，该参数在上述具体步骤使用。

**更新与下一轮。** 每次查找记忆时使用，影响排序。参数保持不变；相关程度、熟悉程度和最近想起的加分会随对话变化。

**含义。** 反复真正聊起过的事情会越来越熟悉。

**调整结果。** 调大更容易想到经常谈的事情；熟悉加分会逐渐趋于稳定，不会随次数无限增大。

**具体影响。** 熟悉度 1−exp(−重温次数/5) 的系数；多次重温逐渐趋于饱和。

**处理过程。** 见本组“相关性本身的分量等参数的处理流程”，该参数在上述具体步骤使用。

**更新与下一轮。** 每次查找记忆时使用，影响排序。参数保持不变；相关程度、熟悉程度和最近想起的加分会随对话变化。

### 同样情绪的旧事的分量 · emotion

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `memory.rankWeights.emotion`。默认：`0.05`。

**含义。** 当前情绪与记忆里的情绪标签相符时，给这条回忆额外优势。

**调整结果。** 调大更容易出现情绪带起的联想，比如低落时想起相似经历；前提仍是它进入搜索候选。

**具体影响。** 当前情绪与记忆情绪标签匹配、再按发生时间衰减的系数。

**处理过程。** 见本组“相关性本身的分量等参数的处理流程”，该参数在上述具体步骤使用。

**更新与下一轮。** 每次查找记忆时使用，影响排序。参数保持不变；相关程度、熟悉程度和最近想起的加分会随对话变化。

### 刚刚想起的旧事的分量 · activation

保存位置：agents/<id>/config.yaml（根文件保留公共默认值） → `memory.rankWeights.activation`。默认：`0.1`。

**含义。** 刚被想起的记忆有短暂热度，这里决定它对排序影响多大。

**调整结果。** 调大更容易连着聊同一件事；热度会按 activationHalfLifeMinutes 消退，不是永久置顶。

**具体影响。** 最近激活记忆的加分系数，按 activationHalfLifeMinutes 快速衰减。

**处理过程。** 见本组“相关性本身的分量等参数的处理流程”，该参数在上述具体步骤使用。

**更新与下一轮。** 每次查找记忆时使用，影响排序。参数保持不变；相关程度、熟悉程度和最近想起的加分会随对话变化。
