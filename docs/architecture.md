# 架构

[完整手册](manual.md) · [配置指南](configuration-guide.md) · [内部流程](internals.md)

```text
Telegram / HTTP / 定时脚本
        ↓ Event v1
第一层：渠道接入与平台发送
        ↓ Event v1
第二层：JSONL 原始记录 + SQLite 索引 → 定时轮询新触发
        ↓ 当前批次 + 历史视图 + 默认回复位置
第三层：人格 / 记忆 / 状态 / Skills → ContextBundle
        ↓ 每次独立的 RunRequest
第四层：Pi 模型调用 → 工具 → 模型调用 → RunResult
        ├─工具记录─────────→第二层保存
        ├─完整文字块/附件───→第二层发送队列→第一层
        └─整轮结束─────────→第三层后台心情与记忆强化
```

## 替换边界

| 模块      | 入口                                            | 可以替换什么                                 |
| --------- | ----------------------------------------------- | -------------------------------------------- |
| contracts | `EventSchema / Channel / Executor`              | 自有协议，不依赖 Pi 类型                     |
| layer1    | `ChannelRegistry`                               | 新增 QQ、邮件等渠道；平台对象在此归一化      |
| layer2    | `Runtime / Store / Journal / Outbox / History`  | 存储与轮询实现、发送队列、压缩算法           |
| layer3    | `ContextBuilder / MemoryService / Intelligence` | 召回策略、向量存储、提示词、状态更新         |
| layer4    | `PiExecutor / appTools / mcpTools`              | 执行底座；Runtime 可注入其他 ExecutorFactory |
| admin     | `servers()`                                     | 管理界面与外部 HTTP 接口                     |
| scheduler | `Scheduler` + `agents/<id>/schedule.ts`             | 触发脚本。只产生统一事件                     |

组件在同一 Node 进程运行。调度脚本及 MCP stdio 服务是子进程。没有按渠道分开的长期 session；Pi 的临时会话只活到本次 Run 结束。

## 原始记录与索引

先把事件追加并 flush 到 agent 的 JSONL，再写 SQLite 索引。事件 ID 在同一 agent 内去重。长工具结果另存 JSON，Shell 原始字节持续写 `.stdout`，工具完成后追加结果事件。附件落到稳定路径并有 `.json` 状态清单。

文件可直接被 AI 读取。SQLite 保存事件索引、运行/投递状态、历史摘要检查点和记忆索引缓存。记忆检索索引另有 `.runtime/search-index.json` 文件，保留强化强度。丢失 SQLite 后可从文件重建经历；旧触发不会重新执行，无法确认的投递需人工检查。

打断时删除未交接回复，同时清理其运行结果正文和含这些内容的调试快照；摘要已包含它时失效重建。删除操作用临时 ID 清单保证重启能完成清理，清单不保存正文，完成即删除。

每次启动停止上次工作和未接手的旧触发。未发送的可靠队列继续发送；上次停在平台请求中的投递标为 `uncertain`，不盲目重复提交。

## 第二层

一次轮询把一个 agent 的新触发一起接手；新触发再到就取消当前工作。等执行器结束后进入下一轮，避免两个执行器同时改同一 workspace。旧工具结果仍保存；同一 agent、同一 channel/conversation/thread 未交接的回复物理删除，已交给第一层的任务继续发送。

原始记录按到达顺序 `seq` 排列，另存来源时间。历史视图超过 600k token 时，把较老部分批量总结，目标回落到 350k。每条工具结果自动只带末尾 200 token；完整原文可查。

发送全局串行。已确认的分段记下进度；确定失败退避重试，不确定结果停止自动重试。私聊不自动分给其他 agent；群聊已送达的消息按明确参与关系成为其他 agent 的新经历。

## 第三层

`memory.json` 由 agent 用 Skill 维护。系统检查文件、生成检索句、分片向量化，混合词法与向量排名，再考虑强度、重要性、熟悉、情绪关联和短期激活。语义 API 失败回落到词法，重排失败沿用融合顺序。时间邻居与一次自然联想补充上下文，受共同预算约束。

检索描述和向量主要在睡眠时维护；可改成文件稳定后的后台维护。网络维护不占住索引写锁，召回仍可工作。新文件即使还没向量，也能词法搜索。

`state.json` 仅当前快照，读取时补算自然回稳。第二层计算距当前渠道上次提交文字块的间隔。第四层真正结束后，快模型根据本轮输入、输出、工具摘录和结束原因提出增量；限幅后应用。它同时标出实际重温的候选记忆，允许为空。已取消或沉默的回合也按真实内容判断，不等渠道送达。

上下文顺序：基础规则 + 人格 + 项目/Skills + 表达倾向；然后历史视图；然后本轮召回、状态和当前事件提示；最后就绪图片。第三层默认预算 32k。最终检查模型窗口，预留输出和安全余量；只有极限保护才要求额外压缩历史。工具循环每次请求前也检查容量。

## 第四层

每次 new Pi Agent，只使用给定上下文和注册工具。使用官方文件/Shell/搜索工具，不加载 Pi 的编程人格或磁盘 session。模型文本按完整句子发出，消息结束时补交剩余段落；代码围栏期间保留到消息结束。思考内容和工具参数不当作聊天发送。

每条 assistant 消息有 response_id，文字块有 chunk_index。run_id 表示整个工具循环。结束时不重新发送已经提交的文字。沉默工具终止本轮；发送工具把附件复制到稳定位置后入队。
