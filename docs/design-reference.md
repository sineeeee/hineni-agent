# 个人 Agent 系统实施需求

更新日期：2026-11-01

本文供后续设计、编码和验收使用，合并四层职责、第二层记录与压缩、第三层记忆与状态编排，以及输入、执行和发送的完整流程。四层主要行为已经确定；参数是可调初值，依赖接口和实际效果在实施时验证。

文中的行为要求来自已确认的讨论。技术选型属于优先验证方案；标为“建议初值”的参数是便于实施的起点，经过验证后调整。涉及参数的配置应集中管理，并明确单位和作用范围。

## 1. 要做什么

构建一个长期运行的个人 Agent 系统，用于日常聊天、处理个人事务、使用工具，以及由定时器或脚本触发主动行为。首先部署在 Linux VPS 或云电脑上，支持迁移到本地服务器。

系统自己掌握消息记录、人格、记忆和完整上下文编排，复用成熟的消息接口、模型调用与工具执行能力。程序、配置、数据、Skills 和运行依赖分开管理，方便检查、备份和迁移。优先保证稳定好用。

支持多个 `agent_id`。每个 agent 有独立的人格、经历、记忆、情绪、dream 和当前事项。共同群聊可以形成各自的共同经历；跨 agent 获取信息通过明确的消息交流或文件读取完成，并保留来源。

## 2. 四层框架

| 层                     | 职责                                                          | 交接内容                                                           |
| ---------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------ |
| 第一层：消息接入       | 接入平台、收发文字和附件、实现发送效果                        | 将统一入站消息主动交给第二层；接收统一发送指令；返回发送结果       |
| 第二层：路由与原始记录 | 保存各 agent 的完整经历、检查新增消息、确定处理对象和回复去向 | 给第三层提供事件及记录；接收第四层执行记录；将回复交给第一层       |
| 第三层：Context 编排   | 组织人格、历史、记忆、状态、当前事项、图片及工具结果          | 给第四层提供本次工作的完整上下文，并管理执行中后续模型请求的上下文 |
| 第四层：Agent 执行     | 调模型、连续使用工具、运行脚本、生成回复和文件                | 持续交回执行记录，最终交回回复、附件或沉默结果                     |

四层作为同一后端程序的四个组件实现。第一、第二层使用我们定义的统一协议。平台协议和平台差异封装在第一层。第二、第三层紧密配合：第二层提供近期经历视图，第三层加入记忆与状态，并检查最终请求容量。

每个 agent 有一条连续的主经历，包含各入口的私聊、群聊和主动事件。第三层从中选择本次所需内容。第四层每次工作的跨次历史由第三层提供，执行期间保留本次工具循环需要的临时上下文。

基本路径：

```text
平台消息 → 第一层封装 → 第二层保存并发现新增 → 第三层编排 → 第四层执行
                             ↑                         │
                             └──── 工具过程与结果 ──────┘

第四层产出 → 第二层确定去向并提交发送 → 第一层发送 → 第二层记录实际发送结果
```

## 3. 第一层：实现要求

### 3.1 接入方式

首个入口实现 Telegram 私聊和群聊。优先验证 grammY，使用其收发与附件接口，在外面包一层我们自己的适配器。

其他入口按同一协议扩展：QQ、邮件、Webhook 等。Satori／Koishi 适配器体系作为多平台候选，接入时仍由第一层转换成自己的协议。QQ 的官方机器人与普通账号接入属于不同方案，实施 QQ 时再选择。

每个接入账号有独立的 `channel_account_id`，用于区分多个 bot、邮箱或其他入口账号。配置其凭据和投递目标；具体消息归哪个 agent 由第二层路由决定。

Telegram 首先采用长轮询接收。接收程序持续工作，收到消息后完成封装并主动投递给第二层；模型工作和附件发送可以独立进行。

### 3.2 入站统一消息

协议第一版使用 `protocol_version: 1`。以下字段表达必需语义，编码时可以按需要组织为嵌套对象。

| 字段                                      | 含义                                                             |
| ----------------------------------------- | ---------------------------------------------------------------- |
| `event_id`                                | 本系统生成的事件编号，重试投递时保持相同                         |
| `platform`、`channel_account_id`          | 来源平台及接收账号                                               |
| `source_event_id`、`source_message_id`    | 平台提供的事件与消息编号，供去重和追溯                           |
| `conversation_id`、`conversation_type`    | 聊天位置，以及私聊、群聊、邮件等类型                             |
| `thread_id`                               | 平台的话题或邮件线程编号，存在时提供                             |
| `sender_id`、`sender_name`、`sender_type` | 发言人身份、显示名，以及用户或 bot 等类型                        |
| `occurred_at`、`received_at`              | 平台事件时间和系统接收时间，统一采用 UTC 时间戳                  |
| `text`                                    | 消息文字及附件说明文字                                           |
| `attachments`                             | 附件列表，见下节                                                 |
| `reply_to_message_id`                     | 被引用或被回复的消息编号，存在时提供                             |
| `reply_target`                            | 可交回第一层使用的回复定位信息，包括平台、账号、聊天位置和话题等 |
| `raw_payload_ref`                         | 原平台事件的保存引用，供排查及未来补字段                         |

平台缺少的字段按缺省值处理，接收时间与平台时间分别保留。相册等组合消息保留平台分组编号，方便后续关联。

### 3.3 图片和文件

接收图片和文件后，将内容保存到系统控制的附件目录，生成 `attachment_id`。附件信息包含原文件名、媒体类型、大小、存储引用、平台文件编号，以及可用或下载失败的结果。

存储名称由系统生成，原文件名作为元信息保留。多个服务使用不同文件路径时，由存储引用解析成各自能访问的路径。

第一层收到消息后先提交文字、附件编号、预定存储位置及当前可用情况，下载在后台继续。其他消息接收和出站发送照常进行。

出站文件使用存储引用，由第一层读取并上传。图片发送可以选择图片展示或文件附件形式。平台大小限制由适配器检查，并返回明确结果。

#### 附件就绪事件

下载使用临时文件，成功后切换到最终路径。第一层通过同一协议提交`attachment_ready`或`attachment_failed`事件，带原消息编号、附件编号及成功位置或失败原因。原始消息和附件关联保持不变，后续事件更新其可用情况。

附件结果继承原消息的agent路由和回复目标。第二层轮询到附件结果后，沿新触发规则处理；同批已收到原消息和就绪事件时，一起组织为当前可用的附件。尚未完成时，模型可先看到文字与附件未就绪的事实；就绪后才将图片转换为视觉输入或读取文件。失败也作为明确事件交给模型。重复提交同一附件结果按事件编号去重。

### 3.4 与第二层交接

第一层主动调用统一入站接口。第二层保存成功后返回确认，第一层据此完成交接。失败时用相同 `event_id` 重试，第二层按事件编号及来源编号去重。

重试期间保留待交付事件。待交付队列用于可靠交接；长期原始记录归第二层保存。第二层检查的是自己的新增记录与处理进度。

Telegram 拉取进度与交接确认要配合，保证持久化失败后仍能重试这条消息。

### 3.5 出站统一指令

| 字段                         | 含义                                                     |
| ---------------------------- | -------------------------------------------------------- |
| `delivery_id`                | 本次发送批次编号，供去重和结果关联                       |
| `action`                     | `send_message`或`react_to_message`，由第一层执行平台操作 |
| `message_ref`、`emoji`       | 表情动作的原消息引用和表情；普通发送可省略               |
| `agent_id`、`run_id`         | 产生内容的 agent 和工作编号                              |
| `response_id`、`chunk_index` | 原模型回复编号及第四层提交的文字块顺序                   |
| `target`                     | 目标平台、接入账号、聊天位置和话题                       |
| `parts`                      | 按顺序发送的文字、图片或文件，各部分有自己的编号         |
| `reply_to_message_id`        | 可选的引用回复目标                                       |
| `presentation`               | 输入状态、发送延迟、分句方式和间隔等效果配置             |

第一层接收后负责执行发送效果：显示正在输入、等待、拆分文字、按顺序发送、上传附件。平台支持情况由适配器处理，通用字段映射到对应平台接口。

**发送批次交给第一层后，按原计划发完。** 后续新消息打断的是第四层正在进行的工作；第一层已接收的发送批次继续执行。第二层到第一层按持久化的入队顺序号串行交付，第一层逐批执行发送效果和发送；首版使用单一出站队列。批次及分段保持顺序，发送结果逐项记录。模型和工具工作可以继续进行。

第一层按实际发出的部分返回结果：`delivery_id`、部分编号、平台消息编号、实际内容、发送时间及成功或失败原因。第二层分别保存待发送内容与实际发送结果。

消息表情与文字、附件共用出站队列和投递回执。适配器提供当前目标是否支持消息表情及可用范围；无法确认的能力在调用时校验，不支持或被平台拒绝时返回明确结果。表情回执只更新记录。

确认失败的发送可重试；平台是否接受尚不明确时保留该事实，按平台能力核对。发送重试以避免重复投递为目标。

以下是首版配置项清单；具体数字均为建议初值。

| 配置项                                 | 建议初值                   | 控制什么                                   |

| `channels[].poll_timeout_seconds`      | 30                         | Telegram 长轮询单次等待时间                |
| `ingress.endpoint`                     | 部署时设置                 | 第二层统一入站接口位置                     |
| `ingress.auth_ref`                     | 部署时设置                 | 内部接口认证配置                           |

## 4. 第二层：记录、路由与历史压缩

### 4.1 保存什么

每个agent维护一条连续的主经历。保存收到的消息、内部事件、模型回复、工具名称与输入参数、已取得的输出或错误、附件关联和实际发送结果。每条记录带事件编号、agent编号、时间、来源及必要的工作编号。长工具输出单独保存，记录里保留可读取的位置。

完整记录与供模型使用的历史视图分别维护。首版建议以SQLite保存结构化事件和处理进度，附件及长输出保存在文件目录；通过工具提供原始记录查询，并在项目说明里写清存储位置和读取方法。具体表结构在实施时确定。

### 4.2 保存记录与启动推理分别判断

第二层一次轮询读取同一agent已经到达的全部新触发事件，一起启动一次编排，以最新事件作为默认回复来源，模型结合整批内容决定先做什么。处理开始后又到达新触发，照常打断。第二层按事件类型决定处理方向。记录中的`event_type`用于调度，模型接口的`role`在第三层转换，两者分别保存和使用。

| 事件类型                                | 内容                                           | 下一步                                 |
| --------------------------------------- | ---------------------------------------------- | -------------------------------------- |
| `incoming_message`                      | 用户发来的消息                                 | 路由到对应agent，启动新一轮处理        |
| `internal_event`                        | 定时任务、脚本事件、主动聊天机会、梦境分享机会 | 启动新一轮处理，允许最后沉默           |
| `tool_call`、`tool_result`              | 工具参数、结果、错误或部分输出                 | 保存，由原工作继续处理                 |
| `agent_reply`                           | 第四层封装好的中间或最终回复文字块、附件       | 保存并入发送队列，立即交第一层处理     |
| `attachment_ready`、`attachment_failed` | 已接收附件的下载结果                           | 关联原消息更新附件情况，作为新触发处理 |
| `outbound_action`                       | 模型请求对既有消息点表情                       | 保存并进入出站队列，由第一层执行       |
| `run_finished`                          | 正常完成、沉默、取消、失败或达到执行上限       | 记录本轮结束，不触发新推理或发送       |
| `delivery_result`                       | 文字、附件或表情操作成功、失败或尚未确认       | 更新投递记录，按发送策略处理           |

用户消息和内部触发统一采用“新事件打断当前工作”的规则。第二层发现需要推理的新事件后，按第6.7节取消旧工作，再交第三层编排；模型根据已有触发消息、工具过程和结果决定继续哪件事。已有记录沿正常历史视图进入上下文，任务先后由模型判断。工具结果、自身回复、表情动作及发送回执继续走各自记录或出站方向。表情反应首版作为记录处理，不自动触发群聊接话。

同一事件用稳定`event_id`去重，并记录每个接收agent是否已接手、对应的`run_id`及完成或中断结果。接手与分配工作编号一起持久保存，轮询重复看到记录时沿用处理进度。重启后已开始但中断的工作保持停止，尚未接手的事件正常处理。

工具结果和自身回复的追加只走表中对应路径。群聊消息按参与关系分发到各agent的经历；其他参与agent的文字发言也可以触发本agent处理，由模型决定接话或沉默。首版暂不设置自动接力轮数、点名窗口或参与概率限制，允许持续互聊。自身发送回流按账号和平台消息编号关联原投递，避免再作为自己的新消息触发。群聊参与优化留待实际使用后讨论。

### 4.3 统一入口与内部事件表达

第一层适配器、定时脚本和外部调用方使用同一版本的事件协议，提交到第二层统一事件入口。共享字段为`protocol_version`、`event_id`、`event_type`、`source`、`occurred_at`、`text`和可选附件；第二层补接收时间。内部事件明确指定`agent_id`，平台消息通过账号和聊天位置路由到agent。平台特有字段及`reply_target`沿第3.2节保留。

入口验证身份、允许的事件类型和目标agent，保存成功后确认。提交重试保持相同事件编号。定时脚本直接提交`internal_event`，第二层照常轮询自身记录。Webhook提供这套提交能力，平台协议转换仍由第一层负责。

定时器、脚本和未来的Webhook统一提交`internal_event`，包含`event_id`、`agent_id`、`source`、`occurred_at`、`text`及可选材料引用。来源可以是`scheduler`、`script`或`dream`。普通回复回到消息来源；内部事件产生的主动回复使用agent配置的默认渠道。

第二层保存事件的真实来源。第三层将它组织成明确标注的事件消息；首版使用模型接口的`user`角色承载，正文注明“内部事件，并非用户发言”。长期人格和行为规则放在system说明里。事件文字可自然生活化，同时保留时间、来源和明确任务。

主动聊天事件示例：

> 内部事件：一次主动联系的机会。现在是{时间}。结合最近的交流、你还惦记的事情和当前状态，想想是否有自然的话想对对方说。有就通过默认渠道联系，没有也可以保持安静。

定时办事事件示例：

> 内部事件：之前安排的任务到时间了。任务是{任务内容}。请结合已有记录执行，完成后通过默认渠道反馈。

梦的内容先作为产物保存，需要考虑分享时再提交一次“梦境分享机会”，附梦境内容或引用。模型决定是否表达；实际分享及后续交流进入通常的记忆流程。事件记录表达的是一次触发，完成情况由后续执行结果记录。

#### 跨入口回复

默认回复本轮最新触发的来源，内部主动事件使用默认渠道。提供可选回复目标，目标引用已有事件或已配置的聊天位置，由第二层解析成第一层所需地址。上下文保留每条事件的来源、发言人及所在群聊，支持模型判断适合在哪里表达。

第四层提供`send_message(target_ref, parts)`工具，允许先在当前入口确认，再继续工作并向另一个入口发送结果。工具通过第二层保存并交第一层发送，返回投递编号或已知结果；同一内容只通过一次发送路径交付。普通中间及最终回复仍走默认目标。目标支持配置别名，如`tg_private`、`mail`，映射到明确账号和聊天位置；可用别名在工具说明或项目文档中提供。工具定义使用我们自己的协议，Pi类型仅留在第四层适配器中。

### 4.4 历史按容量压缩

第二层提供“较早历史摘要＋连续的近期原文”。依据容量批量压缩较老的一段，压缩后留出空间，再继续追加对话。时间戳用于理解经历，保留范围以容量和完整消息边界决定。

压缩是独立模型请求。输入为上次摘要与本次选中的较老经历，输出新的历史摘要；保存成功后替换历史视图里的对应部分，原始记录继续保留。失败时沿用原视图；总容量检查未通过时先处理容量问题，再发下一次模型请求。压缩期间新增消息继续保存，摘要只覆盖本次选定的范围。

摘要保留话题进展、具体事件、用户表达的偏好和修正、未完成事项，以及工具执行已取得的结果。保留不确定性；工具缺少结果时如实记为未确认。摘要属于第二层近期经历整理，长期个人记忆按第三层Skill流程另行产生。

压缩提示词起步模板：

> 根据已有摘要和给定的较早记录，整理一份供后续交流使用的历史摘要。保留具体事件、重要措辞和修正、当前事项、未完成任务及已有工具结果。合并重复内容，说明变化和仍不确定的地方。只总结给定范围，不推断没有记录的结果。控制在{摘要预算}内，输出摘要正文。

历史视图中，较老工具结果默认展示工具名、必要参数及结果末尾最多200token，并提供完整结果位置；错误、退出状态和关键产物信息优先保留。正在处理的工具结果按本轮需要提供，过长时分页或截取并标明原始位置。

### 4.5 主动查询原始记录

提供`search_history(query?, time_range?, run_id?, cursor?)`和`read_history(record_id, cursor?)`，返回原始消息、发言人、时间、来源及工具记录。结果受条数和token预算约束，长记录可继续分页。查询范围默认属于当前agent的经历。原始记录工具供模型核对细节，历史压缩由程序维护。

### 4.6 第二层起步配置

| 配置                             | 建议初值      | 控制什么                                         |
| -------------------------------- | ------------- | ------------------------------------------------ |
| `routing.poll_interval_ms`       | 500           | 检查已保存新增记录的间隔                         |
| `routing.default_target`         | 每个agent配置 | 主动回复的默认发送位置                           |
| `history.compaction_model`       | 部署时配置    | 生成历史摘要的模型，须容纳待压缩材料，必要时分批 |
| `history.summary_max_tokens`     | 12,000        | 历史摘要的输出预算，计入历史视图                 |
| `history.tool_tail_tokens`       | 200           | 较老工具结果保留的尾部长度                       |
| `history.search_max_items`       | 20            | 原始记录查询每页最多条数                         |
| `history.tool_result_max_tokens` | 4,000         | 一次历史查询或读取返回的总预算                   |

第二层独立按自己的历史容量阈值生成视图，第三层独立管理人格、记忆等预算。正常编排直接拼接；最终请求接近模型可用输入极限时，才走强制压缩第二层的兜底路径。容量初值见第5.9及5.11.6节。

### 4.7 定时与随机触发：一个可修改的脚本

首版使用一个定时脚本，统一放置各agent的固定时间规则和随机触发逻辑。支持cron表达式、固定间隔，以及指定活动时段内的自定义随机间隔。cron表达式由脚本中的调度库解释，脚本自己等待到点，再按统一协议向第二层提交事件。

例如：北京时间早八点到晚八点，每次抽取十到二十分钟的间隔，到点发送一条主动聊天机会。其他时段、跳过某小时、分时段采用不同概率等规则，都在脚本中编写。模型最后说话或沉默，沿通常编排流程决定。

脚本文件和规则说明长期保存。脚本运行中计算的下次时间只保存在内存里；每次启动或重启从头初始化。cron从启动后的下一个匹配时间继续，停机期间错过的时刻跳过；随机间隔重新抽取，普通间隔重新计时。已经提交到第二层的事件按原有记录和处理进度处理。

触发脚本的职责到事件提交为止。模型执行和打断继续由第二、四层处理，完成情况体现在普通对话及工具记录里。当前有哪些定时行为，直接查看脚本及其中的规则说明。

### 4.8 脚本运行与修改

VPS使用现成的服务管理能力维持定时脚本运行，首版可用systemd；容器部署则使用对应的服务运行方式。服务启动和故障重启均采用上述从头初始化规则，同一部署只运行一份该脚本。

项目说明写清脚本路径、规则所在位置、时区、统一事件入口、日志位置及重启方法。用户和agent使用已有文件工具修改脚本，修改后调用一个`restart_scheduler`工具让新版本生效。该工具只重启定时脚本，返回启动是否成功及失败日志位置；主agent服务继续运行。查看规则和排查错误使用现有文件、终端工具即可。

| 配置                        | 建议初值        | 控制什么                   |
| --------------------------- | --------------- | -------------------------- |
| `scheduler.script_path`     | 部署时设置      | 唯一定时脚本的位置         |
| `scheduler.timezone`        | `Asia/Shanghai` | cron和活动时间段使用的时区 |
| `scheduler.service_name`    | 部署时设置      | 重启工具对应的服务名称     |
| `scheduler.events_endpoint` | 第二层统一入口  | 触发事件提交位置           |
| `scheduler.credentials_ref` | 部署时设置      | 提交事件的认证配置         |
| `scheduler.log_location`    | 部署时设置      | 标准输出和错误日志位置     |

具体cron表达式、活动时段、随机间隔范围、目标agent和触发文字写在脚本里，按实际需求修改。重启重新计时属于首版固定行为。

## 5. 第三层：记忆、状态与上下文编排

### 5.1. 第三层做什么

第二层给来一段近期经历：较早内容的摘要、最近聊天原文，以及相关工具记录。第三层加上人格、这次想起的旧事、当前心情和念头，交给第四层。

一次交流的主要过程是：

```text
第二层的近期经历＋当前消息
          ↓
读取人格和当前状态
          ↓
整理搜索线索，寻找相关记忆
          ↓
加入短期激活、时间相邻片段和随机联想
          ↓
按预算拼好上下文 → 第四层回复或工作
          ↓
正文交回第二层；更新当前状态和记忆强度
```

长期记忆由 agent 通过 Skill 写。程序负责索引、检索、衰减和拼接。每个 agent 使用自己的文件和索引。

**回复篇幅与语气先由 System Prompt 控制。** 主模型根据完整交流自行判断说多少。检索前的小模型只整理查询线索，程序也不划分“工作／闲聊模式”。

#### 第二层与第三层的容量分工

第二层维护完整原始记录，并生成“较早历史摘要＋近期原文”的上下文视图。我们讨论过最近24小时原文加前一天摘要，最终改为**按容量批量压缩**：不固定两天或自然日，接近预算时整理较老的一段，保留连续的近期原文。压缩后腾出一块空间，后续对话继续追加；不是每次回复都调用压缩API。原始记录始终保留。

第三层管理自己加入的人格、记忆、状态等材料的预算。程序在拼装时计数、选择和缩减可选内容，第二层的历史压缩仍由第二层完成。最后发给第四层前，对整份请求再检查一次总容量。

### 5.2. 四个主要文件

| 文件          | 内容                                               | 谁更新                     | 什么时候读                         |
| ------------- | -------------------------------------------------- | -------------------------- | ---------------------------------- |
| `persona.md`  | 身份、性格、说话习惯、对话样例                     | 明确编辑人格时更新         | 每次回复                           |
| `memory.json` | 一段段经历、当时感受，以及从经历中形成的认识       | agent 的记忆 Skill         | 检索选中后读取；agent 也能主动翻看 |
| `state.json`  | 当前心情、驱动力、念头、当前关注点、短期活跃的记忆 | 程序根据时间和模型反馈更新 | 每次编排                           |
| `config.yaml` | 模型、预算、更新频率、衰减和联想等参数             | 我们或有权限的 agent 编辑  | 加载配置时                         |

文件放在 `agents/{agent_id}/` 下。位置和读写方法写进项目说明，agent 可以用普通文件工具查看。

程序另外维护一个内部索引，建议起步用 `.runtime/memory-index.sqlite`。里面存搜索数据、记忆强度和维护进度。这是程序数据，不要求你手工整理。

`state.json` **只保留当前快照**，每次覆盖更新。仍在影响它的原因可以保留一句，已经过去的原因退出。值得长期记住的感受，交给 Skill 写进记忆。更新时间用于计算衰减，不另建连续情绪日记。

### 5.3. 记忆文件保持原来的样子

沿用你现有 Skill 的字段，只增加稳定的 `id`：

| 字段          | 含义                                             |
| ------------- | ------------------------------------------------ |
| `id`          | 程序补充的记忆编号，后续更新索引、读取细节时使用 |
| `agent_name`  | 这是谁的记忆                                     |
| `type`        | 沿用现有字段，默认 `event`                       |
| `people`      | 实际参与者                                       |
| `occurred_at` | 事情发生时间；不知道精确时间时允许日期范围或未知 |
| `summary`     | 简短回忆                                         |
| `details`     | 具体经过及当时的理解                             |
| `emotion`     | 当时的情绪方向、标签、强度和感受                 |
| `importance`  | 1～5，表示这段经历对它的重要程度                 |

新的认识直接写在 `summary`、`details` 里。比如“后来我试过另一种办法，发现更顺手”，也是一段经历。人物理解、关系变化和自我认识都使用这个格式。

示例只用于说明结构：

```json
{
  "memory": [
    {
      "id": "m_001",
      "agent_name": "示例角色",
      "type": "event",
      "people": [{ "name": "小林", "role": "一起讨论的人" }],
      "occurred_at": "2026-11-01",
      "summary": "我们重新聊了以前常用的那个办法。",
      "details": "我一直觉得 A 很顺手。这次他解释了 B 的好处，我觉得有道理，打算下次试试。",
      "emotion": {
        "valence": "mixed",
        "labels": ["好奇", "有些不服气"],
        "intensity": 0.4,
        "feeling": "我听懂了，但旧习惯还很熟悉。"
      },
      "importance": 3
    }
  ]
}
```

旧经历、新认识分别保留。检索时根据语义和发生时间寻找，必要时再带出时间相邻的两三条。记忆里保留自己的理解，需要核对原话时再去第二层查记录。

### 5.4. 记忆怎样写进去

有三个入口：agent 自己想记、你明确要求记、睡眠时段安排一次 Skill 回顾。它们都使用同一份记忆格式。

定期回顾从“上次已经看完的位置”接着读第二层经历。这样某天延迟执行，也能补上遗漏。材料太多就分批；每批成功保存后再更新进度。没有值得记的内容，也可以结束本批回顾。

Skill 关心具体经历和个人意义：有触动的事情、改变看法的交流、有趣的小细节、做事时的感受。新奇、重复和情绪冲击可以影响选择，但不要求每天必须总结出一种认识。

程序可以偶尔加一句“这次也留意一个普通的小细节”，让日常小事有机会被留下。这是额外机会，平时 Skill 本身也允许记小事。

写入时先检查格式，再整体保存。程序只给缺少编号的新条目补 `id`。同一次保存的重复提交合并；真正发生了多次的相似经历继续分别保留。

### 5.5. 搜索数据怎样更新

#### 为每条记忆准备一个检索属性

程序根据记忆生成一段短的 `search_text`，说明这件事及可能唤起它的说法；也可附少量关键词。它保存在索引里，agent 仍然写自然的记忆正文。

默认用于向量化的内容是：**检索描述＋摘要＋细节＋人物**。全文搜索也能查这些内容。因此辅助描述提得不够好时，原本的细节仍有机会被找到。

这是一种起步方案，之后比较“只用正文”和“加入检索描述”的实际效果。更换方案可以重建索引，记忆文件保持原样。

#### 更新分两种速度

- **平时发现变化：** 写入通知或低频检查发现新记忆，先更新全文索引。还没生成向量的记忆也能查到。
- **睡眠时段维护：** 批量补检索描述、生成新增或改动条目的向量，并更新索引。具体钟点待设。

也可以把向量更新改成“变更后稍等两分钟，合并处理”，看实际费用和及时性再选。

维护顺序是：

```text
读取新内容 → 校验 → 更新衰减快照
→ 补检索描述 → 生成向量 → 切换到新索引 → 保存进度
```

遗忘在每次读取时按经过时间计算，不必等维护任务。维护失败时保留能用的搜索部分，失败条目下次再处理。检索结果最后对照当前记忆文件，使用当前版本的正文。

### 5.6. 每次回复怎样找回记忆

#### 第一步：整理“这次想找什么”

给一个小模型看当前消息、少量近期交流和当前念头，生成最多三条检索方向。例如把“上次那个后来怎么样了”补成具体的人物、事情或时间线索。

当前原话也保留一路搜索。小模型失败时，直接用原话和最近几句继续查。它只整理线索，不判断回复场景或篇幅。

#### 第二步：从不同角度找

并行查关键词、语义相似度，以及人物和时间。把结果合在一起，去掉同一条记忆的重复命中，再用重排模型挑出更相关的条目。

排序主要看相关性，再小幅考虑新鲜程度、重要性、熟悉程度、当前情绪和短期激活。分数由各自实现统一处理，不能把不同模型的分数直接相加。

#### 第三步：补相邻经历和自然联想

选中某条后，可以带出发生时间前后相近的最多两条记忆；优先选择人物或内容也有联系的片段。它们计入总名额，不会无限扩展。

随机联想默认开启，每个完整回合只抽一次。它从有语义联系、时间联系或情绪联系的旧事中挑一条。默认每轮统一概率，具体要不要说出来交给主模型。

#### 第四步：先给概括，需要时再看细节

默认最多带十二条相关记忆，另有最多一条随机联想，共用记忆预算。先给 `summary` 和必要的时间、感受；最相关的六条可以展开 `details`。进一步需要细节时，agent 使用下述记忆工具、读记忆文件，或去第二层查原始记录。

有相关材料才加入，不要求每轮填满名额。概括和细节都来自同一份记忆。

#### 预算满了怎样处理

程序先预留必要说明和当前状态的位置，再把排序后的记忆逐条放入剩余预算。条数和token上限同时生效，并计入编号、时间和标签等包装。优先放概括，再给最相关的条目展开细节；某条过长就使用已有摘要，摘要也放不下则跳过该条。随机联想与相关记忆共用预算，空间不足时优先保留相关记忆。

原文按完整条目或段落选择，最终拼装完成后再次计数。没有入选的记忆继续保存在文件里，下一轮仍可被检索。必要说明本身超过配置额度时，明确报告配置问题，由配置调整解决。

#### Agent 可以主动继续查记忆

自动召回是开场材料。模型觉得还缺一段往事、想核对细节或继续追问时，可以主动调用：

- `search_memory(query, people?, time_range?, cursor?)`：用自然语言或关键词搜索当前agent的记忆，返回编号、摘要、时间和后续分页位置。主动查询旧事默认弱化时间衰减，帮助找到较久以前的内容。
- `read_memory(id, cursor?)`：按编号读取完整条目；长条目分段返回，并标明还有多少内容可继续读取。

这两个工具复用同一份记忆和搜索索引。工具说明随正常工具定义提供，文件位置及使用方式写在项目说明里，agent也能直接使用文件工具查看。记忆搜索返回的是记忆内容；需要核对当时原话时，再使用第二层的原始记录查询能力。

主动查到的内容作为本轮工具结果进入第二层记录，并经第三层送给下一次模型调用。它不挤占开场自动召回的名额，但计入整份请求的总容量。每次返回有条数和token上限，剩余结果分页读取。程序返回查询不足、无结果或尚有后续内容的真实状态，模型自行决定是否继续查询。

### 5.7. 遗忘、短期激活与长期强化

这三件事分别计算，记忆正文保持不变。

**长期遗忘：** 一段经历久未重新接触，自动浮现的权重逐渐降低。重要经历淡得慢一些。原记忆仍在，专门查询旧事时可以弱化这个时间影响。

**短期激活：** 刚想起的经历，在接下来一段时间更容易继续想到。存在当前 `state.json` 里，建议半小时衰减一半，几个小时后退出。它比长期记忆淡得快。

**长期强化：** 真正又聊到、再次经历或认真回顾过，才提高长期记忆强度。存在程序索引里。参考鱼的记忆：在当前强度上补回一部分，然后继续随时间衰减。

整轮结束后的后台快模型，在判断心情的同一次请求中返回“这轮确实重新谈到的记忆编号”（`memory_mentions`），允许为空。输入附本轮提供或通过工具读取的候选记忆编号和必要摘录，程序校验编号属于这些候选，并按既有规则每条每轮最多强化一次。主模型专注回复和执行，记忆强化判断不增加另一轮API请求。仅仅被塞进上下文只形成短期激活，不自动算作认真重温。

刚激活的同一条在连续几轮被反复带入时，沿用原来的短期衰减时间；实际重新谈到时可以刷新。这样既能接着想，也不会因为程序循环注入而永远最活跃。

“更容易想到”和“再次讲出来”分别处理。同一段旧事可以持续影响理解，System Prompt 提醒模型根据交流需要提起，避免机械重复。

#### 起步计算方式

这些算式只给程序用：

- 重要性归一化：`I = (importance - 1) / 4`。
- 长期半衰期：`H = 30 × (1 + 2I)` 天，初值范围为 30～90 天。
- 强度衰减：`A_now = A_saved × 2^(-经过天数 / H)`，新记忆初始为 1。
- 再次认真接触：`A_new = A_now + 0.2 × (1 - A_now)`。
- 短期激活：`B = 2^(-经过分钟 / 30)`，到期后从当前状态移除。

半衰期越长，淡得越慢。“熟悉次数”只由真正重温增加，不把生成了几次检索结果当成经历次数。

### 5.8. 心情和念头怎样更新

#### 当前状态里保存什么

| 内容       | 例子                     | 怎样变化                     |
| ---------- | ------------------------ | ---------------------------- |
| 整体心情   | 比平时轻快一点           | 事件影响，随时间回到个人基线 |
| 短期情绪   | 好奇、安心、烦躁         | 事件影响，逐渐淡去           |
| 当前原因   | 还担心刚才没解决的事     | 解决或不再相关时移除         |
| 驱动力     | 想探索、想交流、有点疲劳 | 新事件和时间共同影响         |
| 念头       | 想知道昨天那件事的结果   | 浮现、淡去、解决后退出       |
| 当前关注点 | 正在关注的一个问题       | 模型随交流更新               |
| 活跃记忆   | 刚刚想到的几个编号       | 按第5.7节快速衰减            |

念头和关注点写成短句，不必再拆更多文件。完成或过期的念头退出当前状态；承诺和已有执行情况保存在第二层经历里，定时规则写在单一定时脚本中。

#### 每轮执行结束后后台更新心情

第三层先按经过时间计算自然回稳，再提供本轮状态。第四层整个运行最终结束时发出一次`run_done`回调，相当于本次新建Pi执行实例的工作结束；中间assistant消息结束、工具结束和平台发送回执都不触发心情判断。

第三层直接使用第四层结束回调携带的本轮材料：实际输入、已产生的正文、必要的工具结果摘录、结束原因及候选记忆引用，再结合人格和当前状态，用快模型后台判断心情、情绪、驱动力、念头和关注点的变化，并返回真正重温的记忆编号。正常结束、沉默及被打断都按实际已有内容处理；无有效内容跳过。判断是否启动只取决于第四层本轮最终结束，不取决于文字是否进入第二层或是否发送成功。不按第二层消息逐条判断，也不增加跨轮事件情绪去重机制；快模型按本轮材料理解变化。它不阻塞下一轮主模型，也不要求主模型调用记录心情工具。

每个agent按结束回调顺序串行判断，同一`run_id`的结束回调及判断结果只应用一次，这是防止重复处理同一次回调，不是跨轮去重历史内容；应用时先计算当前状态的时间回稳，再合并有范围限制的增量，不拿旧快照覆盖当前状态。失败沿用当前状态；重置状态或更换归属后丢弃失效结果。下一轮开始得早时可以使用更新前状态，后台完成后供后续编排使用。交流间隔等程序字段由原程序路径更新，不交快模型改写。

查询线索、记忆检索描述和心情判断默认共用`models.fast`服务，各自使用独立请求与提示词。向量及重排模型仍分别配置。仅生成检索描述时不修改记忆正文；情绪判断也不改记忆召回算法。

#### 距离上次回复多久

第二层负责计算间隔，并随本轮经历一次性交给第三层。以本轮开始时刻减去当前回复目标最近一条assistant文字块被第二层接收的时刻；同一`response_id`的多个块归为一条回复，取最近块的接收时间。工具调用、工具结果和第一层再分句不产生新的回复时间。无历史时返回空值，表示首次交流。

第二层提供`target_ref`、`last_response_id`、`last_response_at`、`as_of`及`seconds_since_last_response`。第三层直接存入`state.json`的`conversation_context`当前快照，根据配置渲染提示词。第三层使用第二层提供的值；第一层的发送回执仍用于投递记录，不参与这项间隔计算。

这一间隔表达“距上次提交回复多久”，不是对方实际收到消息的时间。同一轮工具循环复用本轮快照，下一轮由第二层重新计算。已有情绪半衰期继续按状态更新时间计算自然回稳，间隔先作为理解交流节奏的背景。

默认提示词：

> 距离你上次在这里提交回复，已经过去约{间隔}。结合当前交流自然回应。

首次交流时改为“这是你第一次在这里回复”。配置`state.conversation_context_enabled`默认开启，`prompts.conversation_gap`可覆盖这段文字；计入状态上下文预算。

#### 驱动力保留可扩展空间

支持好奇、交流、责任、内省、想念、亲近、疲劳、压力、愉快等维度，每个角色可以选择启用哪些。基本的事件变化和时间回稳先做好。

“压力推高疲劳”“疲劳压低好奇”等互相影响作为可开启的实验项；反复念头升级为执念、无事件的随机情绪漂移也先保留为实验项。

### 5.9. 最后怎样拼给第四层

每次请求按下面的逻辑顺序组织，具体消息格式由模型适配器转换：

1. 基础 System Prompt、人格和表达样例。
2. 项目说明、Skills 入口及必要的工具说明。
3. 第二层提供的历史摘要、近期原文和工具经历。
4. 本轮相关记忆、随机联想、当前状态与念头。
5. 当前消息，或明确标明来源的内部事件。

当前消息只放一次。记忆和状态属于背景材料，和用户实际发言分清楚。工具定义使用模型支持的接口；图片按视觉格式传入，文件带可读取的位置。

同一次工作里的工具结果继续存第二层，再经过第三层入口送入下一次模型请求。人格、记忆选择和随机结果通常复用；新消息开始新一轮编排。

第三层自动加入内容的预算建议为 **32,000 tokens**，采用下面同一套分项上限。有相关内容才放入，额度不要求填满。

| 部分                     |   预算 |
| ------------------------ | -----: |
| 基础说明、人格、风格样例 |  4,000 |
| 相关记忆和联想           | 20,000 |
| 状态、念头、关注点       |  1,000 |
| 项目与 Skill 入口摘要    |  5,000 |
| 时间、标签和余量         |  2,000 |

第二层独立计量自己的历史视图：较早摘要、近期原文和已纳入的工具经历，建议达到60万token时压缩较老部分，压回约35万。第三层按上表控制自己的新增内容，正常情况下直接拼接，分项变化在第三层内部处理。

每次模型调用前执行一次最终容量检查，计入工具定义、图片以及本轮新增工具结果，并排除同一事件的重复计数。兜底输入上限按“模型实际窗口－本次输出预留－计数余量”计算，计数余量建议16,384token。只有达到这个上限时，才强制请求第二层压缩历史。正常60万阈值仍由第二层自己维护；此前80万整体保护线被这条实际容量规则替代。

强制压缩后重新检查。若单条当前消息或附件等不可压缩部分仍放不下，明确返回容量问题或提供按需读取方式，避免反复压缩历史。完整工具调用和结果的关联保留；所有数字都是待实际使用验证的初值。

第四层输出建议分开交回：

```text
disposition      正常结束或不再生成回复，由执行器根据结束方式记录
parts            面向用户的文字、图片、文件
run_done         整轮执行结束的回调，触发第三层后台心情判断
```

正文可在执行过程中按文字块持续交第二层路由、第一层发送。最终输出只提交尚未交付的内容，已发送文字不重复提交。心情更新由第三层后台快模型处理，判断失败时保留原状态，正文照常处理。第二层保留正常执行记录，但第三层不再建立情绪历史库。

### 5.10. 默认提示词

下面是起步模板，实际按角色调整。参数控制程序行为，只有影响模型理解的部分需要写进提示词。

#### A. 基础 System Prompt

> 你是 {名字}，通过聊天入口与对方持续交流，也使用工具处理事情。
>
> 你的身份、性格和表达习惯：{persona}。
>
> 近期记录、旧记忆、当前心情与念头，是你理解这次交流的背景。记忆保留当时的体验和认识，也可能片面。结合眼前的信息判断，需要细节时按项目说明翻看记忆或原始记录。
>
> 平常像聊天一样回应，优先简短自然，参考给定的对话样例。需要解释复杂问题、汇报必要结果或交付内容时，按事情需要展开。做事期间的简单确认、进度回应仍然可以很短。用户明确要求详细或简短时，跟随当前要求。
>
> 可以有自己的看法、偏好和脾气，用具体理由表达。记忆和心情主要影响你如何理解、选择措辞；自然相关时再提起往事或感受。说到完整就自然停下，追问按交流需要提出。
>
> 像日常回消息一样表达，先说这次真正想说的话。简单接话可以只有一句；需要解释和交付时把事情说清楚。称呼、口头禅和人物特色适量使用，让不同话题有不同表达。
>
> 做事时按交流需要说明进展：需要对方等待、出现重要发现或遇到阻碍时，可以简短说一句。普通工具步骤留在执行记录里。开场确认按需要使用，拿到结果后直接讲结果。
>
> 使用实际工具完成行动，按已经取得的结果说明进展。新消息可能打断工作，根据最新消息和已有结果决定继续、调整或停下。
>
> 正文、附件按输出协议交付，心情快照由系统后台维护。选择不再发文字时，调用 finish_without_reply 结束本轮。可以只点一个表情或发一张图片再结束，也可以直接安静结束；已经提交的消息照常发送。

风格样例建议放三四组，覆盖短回应、认真解释、表达不同意见和任务交付。以下仅为普通语气的起步示例，实际随人格替换：

- 对方说“我吃饭去了”：可以回“去吧，回来再聊。”
- 对方问“那个文件找到了吗”：已经查到时回“找到了，在去年的备份里。我把它发过来。”
- 遇到需要等待的查询：可以先说“这个要翻一下旧记录，等我一会儿。”随后实际使用工具。
- 对方要求详细解释：按问题展开，保留必要推理、步骤和例子。

这些是表达样例，事实和完成情况必须以实际记录为准。

#### B. 记忆 Skill

> 回顾 {范围} 内尚未整理的经历，结合已有记忆留下值得保留的片段。
>
> 写清具体发生了什么，以及你怎样理解和感受。大事、小事、出乎意料的回应或逐渐熟悉的习惯，都可以留下。认识变化也自然写进经历里。
>
> 使用现有 memory 格式，以第一人称写摘要、细节和感受。对别人的内心按其表达或自己的猜测如实说明。保留发生时间，最多 {条数} 条，可以没有新条目。
>
> 按项目说明保存，完成后报告这次已经回顾到哪里。

抽中额外小事机会时，附一句：“这次也可以留意一个普通而具体的小细节，即使它没有明显用途。”

#### C. 给记忆补检索描述

> 为每条给定记忆写一段简短的检索描述，保留具体人物、事情和可能唤起它的说法。可以补充少量具体关键词。
>
> 输出编号、检索描述和关键词。内容以原记忆为依据，描述不清时可以少写。这次只加工搜索信息，记忆正文保持原样。

#### D. 本轮查询线索

> 当前消息：{消息}。近期交流：{近文}。当前关注点与念头：{状态摘录}。
>
> 整理最多 {数量} 条寻找旧记忆的查询，尽量说清人物、事情和时间，解释可以从近文确定的指代。可以提出一个有联系的联想方向。未知的信息保持未知。
>
> 输出查询和可用的人物、时间条件。

这个模板只做搜索线索。回复风格与篇幅由主模型遵循基础 System Prompt 自行处理。

#### E. 本轮动态背景

> 当前时间：{时间}。
>
> 浮现的旧事：{记忆概括和必要细节}。
>
> 偶然联想：{有则加入}。
>
> 此刻的状态：{当前心情及仍有影响的原因}。
>
> 还惦记着：{有则加入}。
>
> 交流间隔：{由第二层提供、按模板渲染的间隔说明}。
>
> 这些材料可以影响你的理解和表达，是否提起由你结合当前交流决定。这里只是本轮联想到的部分记忆；觉得还有相关往事没想起来，或需要核实细节时，可以继续搜索记忆、读取完整条目。

这段主要由程序格式化，默认不用另一次 API 把它改写成文字。当前原因和模型上次的简短侧写可以复用，随状态变化调整。

#### F. 后台心情与记忆强化判断

> 根据{人格摘要}理解这一轮已经发生的交流。当前状态为{状态}，本轮输入来源和内容为{输入}，实际产生的回复为{回复}，相关执行结果为{结果摘录}，结束原因为{结束原因}。
>
> 判断本轮带来的心情、情绪和驱动力增量，以及仍在影响当前的原因、念头和关注点。允许没有变化。区分用户说的话、定时提醒和工具结果；中断的事情只按已有结果理解。旧状态本身不是新的刺激。
>
> 候选记忆：{本轮提供及通过工具查到的记忆编号与摘录}。返回本轮确实重新谈到、认真回顾或重新经历的记忆编号 memory_mentions，仅仅作为背景出现的不算，允许为空。
>
> 返回约定的结构化变化字段、memory_mentions及一句简短原因，内容按材料判断，不推断未发生的结果。时间回稳由程序处理。

此提示词只给后台快模型。数值经过程序限幅后应用，记忆编号由程序校验后按原强化规则处理。主模型不用返回这些字段。记忆格式、召回和衰减算法保持不变。

#### G. 项目说明中的记忆入口

> 你的记忆在 {memory_path}，当前状态在 {state_path}，人格在 {persona_path}。日常上下文已提供相关材料。
>
> 想进一步回顾时，可以使用 search_memory 搜索相关经历，用 read_memory 按编号读取细节，也可以用文件工具阅读。搜索结果过长时可以继续分页。需要核对当时原话时，原始聊天的查询方式见 {history_guide}。写记忆使用 personal-memory Skill 和此处约定的格式。

排序建议：先保证相关性，再小幅乘上记忆状态的影响。

```text
Score = R × (0.50 + 0.15A + 0.15I + 0.05F + 0.05E + 0.10B)
```

`R` 是统一后的相关性，`A` 是长期强度，`I` 是重要性，`F` 是熟悉程度，`E` 是情绪关联，`B` 是短期激活。权重统一存为 `recall.rank_weights`，上式即建议默认值。`F = 1 - exp(-真正重温次数 / 5)`；各项均限制在0～1。

该公式用于相关候选之间的排序。阈值、相关性归一化和情绪匹配方法随检索实现固定并测试；数值不是事实可信度。若重排只给名次，使用固定的名次映射，日志标明这种降级。

### 5.12. 保存和失败时怎样处理

- 记忆写入前先验证格式，使用临时文件替换。后台更新遇到文件已被改动时，重新读取后处理。
- 新记忆的全文索引先可用，描述或向量生成失败稍后重试。
- 每个向量带正文版本和模型版本。模型变化时重建，查询与索引使用匹配的向量版本。
- 索引中的搜索数据可以重建；长期强化数据和维护进度属于程序状态，要一起备份。丢失时可用初值恢复搜索，但过去的强化效果无法凭空恢复。
- `state.json` 覆盖保存当前状态。重启后按更新时间补算自然衰减。
- 用户新消息按既定规则打断当前执行。已经保存的记忆保留，未完成的回顾范围留给下一次处理。
- 同一个回合的随机结果和状态变化只应用一次。工具调用多，不会增加抽奖或情绪变化次数。

### 5.13. 首次试用检查什么

先看功能是否符合我们的设想，再调参数：

1. 不同说法能否找到同一段经历；关键词辅助是否真的提高效果。
2. 老经历、新认识能否并存；旧习惯容易浮现时，模型能否结合当前信息判断。
3. 刚想起的事能否顺着聊几轮，之后自然淡去；真正重温能否产生长期强化。
4. 小事和旧事有没有机会出现，又会不会频繁离题或重复。
5. 情绪是否延续、能否因事情解决而缓和；当前状态是否保持简短。
6. 在1M模型下分别用短历史、35万和接近60万的输入验证：普通接话仍能简短，明确要求细节时能展开；超过阈值能批量压缩，第三层超预算会按相关性取舍，主动查记忆能分页读取。
7. 多 agent 文件独立，失败和中断不会损坏记忆；旧索引不会带回已删除内容。

比较同一批聊天样例，记录相关性、正文长度、重复、等待时间和费用。短并不是唯一目标，也要看是否自然、准确、愿意继续聊。

- [DSH 提示词组装](https://github.com/deepseek-ai/deepseek-harness/blob/main/docs/subsystems/system-prompt.zh.md)：稳定说明与动态背景分开。
- [Pi Core](https://github.com/badlogic/pi-mono/blob/main/packages/agent/README.md)：完整上下文由我们提供，工具循环前后保留编排入口。其示例提示词仍需替换为我们的个人 agent 提示词。
- [欲望系统公开说明](https://glama.ai/mcp/servers/Whyomi1122/desire-mcp-server)：驱动力和念头生命周期作为参考；原仓库此前无法直接读取，具体算法尚未验证。

梦境沿已讨论的低占比玩法：偶尔创作，次日产生分享机会，再通过实际对话进入通常记忆流程。定时任务、随机主动联系与Webhook按第4节执行，发送效果按第3节执行。

本节已合并为实施需求；真实长上下文效果和各参数初值仍需验证。

## 6. 第四层：实现要求

### 6.1 执行模型

每次工作接受第三层提供的完整上下文，完成回复或连续工具工作。跨次执行的历史由我们的系统提供；一次工作内部维护模型调用和工具结果的临时上下文。

优先验证 Pi Core 的 `Agent` 或底层执行循环接口，具体导出名按锁定版本核实；文件与终端工具单独接入。每次新工作创建新的执行实例，显式传入第三层上下文，本次工具循环内部保留临时状态。模型接口表达为其要求的 system、user、assistant、tool 等结构，转换由适配代码负责。

人格、历史选择、记忆、状态和工具说明统一受我们的上下文管理控制。每次模型请求前，包括工具结果返回后的请求，提供第三层介入编排的入口。

我们显式提供system提示词，参考框架示例补齐工具使用约定，并使用自己的个人agent人格。接入Skills、MCP及升级底座时检查最终请求，确保附加说明由我们控制。执行库、工具和连接可复用，跨工作历史由第二、三层重建。

### 6.2 一次工作的输入与输出

输入包含：`agent_id`、`run_id`、本次上下文、模型配置、工具集合、工作目录、附件引用、Skills 目录及 MCP 配置。

执行过程中持续交回工具名称与参数、工具结果、错误、产物引用及模型消息。面向用户的中间文字和最终文字都包装为`agent_reply`，第二层接收后立即入发送队列；工具事件只记录或继续原执行。

#### 第四层完成流式封装

第四层接收模型流式事件，只从面向用户的文本中提取增量。普通文字在完整句子或段落边界形成文字块后，立即按顺序提交第二层。文本块结束、进入工具执行前或模型消息结束时，提交剩余可发送文字。代码块等结构化内容保持完整，内部思考、工具参数及状态字段分别记录或处理。

一条模型assistant消息分配一个`response_id`，拆出的块使用递增`chunk_index`，重试时编号保持不变。第一层继续分句时保留这些编号，另加发送部分编号。第四层保存已提交位置，完整消息到达或工作结束时只提交新增内容。原始模型消息与出站块保留关联，在后续上下文中按同一回复整理，避免重复注入文字。

收到取消时，已提交到第二层的块继续发送；尚未形成可发送块的剩余文本保存为部分执行记录。第二层按`response_id`和块序号去重，并分配出站顺序号。这里不等待整个工作结束，也不将逐字流传给第二、第一层。

模型可以先说话、再调用工具、再继续说话；具体是否说开场确认由模型和提示词决定。整轮最终结束时，第四层统一发出一次`run_done`回调，带`run_id`、结束原因及本轮材料。正常完成、主动沉默、取消、失败和达到执行上限均走这个唯一结束出口。第二层将同一次结束保存成`run_finished`记录，第三层据同一回调启动后台判断；两者是同一次结束的记录与通知，不是两次触发。第二层的记录完成与平台发送不作为后台判断的前提。已发送的中间话保持原记录，结束标记本身不再生成聊天消息。

产物包含可读取的存储引用、文件名和媒体类型。声明交付文件时核对可读取，便于第一层上传。

### 6.3 基础工具能力

首版支持读文件、创建文件、修改文件、列目录、搜索文件和内容，以及执行终端命令。VPS 准备 Python、Shell、Node.js 和具体工具需要的依赖。

支持连续调用工具、根据结果继续处理、返回图片内容给支持视觉的模型。网页搜索和网页读取通过专门工具、服务或 MCP 接入。

调用其他模型、Codex 或 Claude Code 等执行程序，可以包装成普通工具：提供任务和必要材料，取得结果，交回主执行流程。其调用同样纳入工具记录。

#### 沉默、消息表情与附件发送

以下工具使用我们的协议。第四层封装调用，第二层保存并路由，第一层完成平台操作。默认目标为当前触发来源，主动事件使用配置的默认目标；附件就绪事件继承原消息目标。

| 工具                   | 输入                                            | 行为                                           |
| ---------------------- | ----------------------------------------------- | ---------------------------------------------- |
| `finish_without_reply` | 无必填参数                                      | 结束本轮，不再请求模型补写文本                 |
| `react_to_message`     | `message_ref`、`emoji`                          | 给指定消息点表情，由第二层解析平台消息位置     |
| `send_attachment`      | `path`、可选`caption`、可选`target`、可选`kind` | 发送已有图片或文件；`kind`可选图片或文件展示   |
| `send_message`         | `target_ref`、`parts`                           | 向指定目标发送文字或已登记附件，适合跨入口回复 |

`finish_without_reply`是明确的结束动作。执行器记录工具调用结果并停止后续模型循环，经统一结束出口发出`run_done`，由第二层保存对应`run_finished`；同批尚未执行的工具跳过并记录原因。它不撤回已入队消息，也不把普通异常、空输出或超时记成主动沉默。先点表情或发附件时，应先调用相应工具取得提交结果，再结束。

`react_to_message`定位到原消息实际所在的聊天位置，不要求模型提供平台API参数。上下文给出可用消息引用，平台能力由适配器说明。工具返回投递编号及当前已知情况：已入队表示接收成功，平台是否完成由投递回执更新。失败保持真实错误，模型可选择其他表达方式。

`send_attachment`先检查文件存在且可读，登记为系统附件并保存到稳定位置，再将`attachment_id`、存储引用、文件名和媒体类型交给第二层。模型通过路径交付，第二层之后使用统一附件协议；第一层按目标平台上传。普通回复中的路径只是文字，实际附件发送以此工具或统一附件parts为准。相同工具调用重试沿用投递编号，避免重复上传发送。

文字、附件和表情动作进入同一个出站队列。工具事件记录与实际出站动作相互关联；一条内容只经一个发送入口提交，工作结束时不再次发送已有附件或文字。只有实际assistant文字更新“距上次提交回复”的时间；表情和纯附件首版保留行为记录，不改变这项文字回复间隔。

### 6.4 Skills

支持扫描配置目录中的 `SKILL.md`，读取名称、描述和路径，将目录信息交给第三层按需组织上下文。模型可以读取完整说明、参考资料和资产，并通过终端执行附带脚本。

优先复用 Pi 已公开的 Skills 加载接口。部署时准备 Skill 依赖、凭据和工具映射。绑定特定应用或操作系统的 Skill，按其实际依赖接入相应能力。

新增 Skill 后提供重新扫描入口。扫描和读取错误应能定位到具体 Skill。

### 6.5 MCP

支持本地进程型 MCP 和远程 Streamable HTTP MCP。配置本地启动命令、参数、环境变量，或远程服务地址、认证引用。

通过成熟 MCP 客户端发现工具、调用工具并转换结果，再注册给 Pi Core。服务提供的资源按需读取。工具描述、资源及使用说明进入上下文的方式由第三层控制。

MCP 连接生命周期、超时、断开反馈和认证需要由接入代码处理。具体服务需要的 OAuth 授权通过部署流程完成。扩展型交互能力按实际 MCP 服务需求逐项验证。

### 6.6 过程记录

工具运行由第四层自行推进，结果出现时追加到第二层。保存可以异步执行；开始下一次工作、组织相关上下文前，确保已取得的记录完成写入。

工具记录至少关联 `agent_id`、`run_id`、工具调用编号、时间戳、名称、输入参数及已取得的输出或错误。接收工具开始事件，结束时追加取得的结果，方便识别执行到哪里。

长输出单独保存，原始记录保留存储引用。保存实际工具结果与供模型阅读的截断内容之间的关联。Pi 生成的临时输出文件转入持久存储。

下一次问“刚才用了什么工具、得到什么结果”时，可由第三层带入相应记录，或使用第二层记录查询工具检索。原始记录查询与摘要方式见第4节，记忆查询与上下文预算见第5节。

取消时保存已经拿到的部分输出。记录中的结果表示系统已经取得的证据；缺少结果表示尚未取得确认，供后续模型如实理解。

### 6.7 新消息、内部事件与打断

用户消息或定时、脚本等内部触发先进入第二层记录。需要交给正在工作的同一个 agent 时，统一打断当前工作：停止当前模型生成，并向正在执行的工具传递取消请求。

第四层保存已有消息、部分工具结果及取消反馈。第二、三层在已取得记录的基础上组织新一轮输入，由模型决定继续、调整还是放弃原事项。

工具取消表示尽力停止当前操作，已经发生的文件修改或外部操作保持其实际结果。对于仍在结束中的工具，后续结果继续关联到原 `run_id`。

第二层已接收为可发送回复的`agent_reply`继续路由和发送，即使随后发生打断。这里指第四层已经封装并提交的面向用户文字块或附件，不包含尚在缓冲的零散片段、工具参数或内部状态字段。取消先被处理时，尚未接收的旧回复停止提交；接收与取消按程序顺序确定。晚到的工具结果继续记录，已取消工作不再直接提交状态覆盖；其最终结束回调可以启动上述后台增量判断。

提示词向模型说明：用户可能随时补充或转换话题，内部事件也可能带来新的事项；模型根据最新事件及已有记录自行决定先做什么、继续什么以及如何回应。人格和表达风格按第5节执行。

### 6.8 重启行为

程序正常关闭时尝试取消正在执行的工作。启动后加载已保存记录，原先中断的工作保持停止，等待后续新消息或明确指令。

执行进程按工作编号管理，使服务停止时能够清理其子进程。异常中断后根据已保存证据呈现执行情况。

第一层已经接收的发送批次属于独立投递。重启后确认已发送的部分保留结果，确认未发送的继续处理；平台接受情况未知的部分保留不确定状态，按平台可核对能力处理，避免无依据地重复发送。

### 6.9 第四层配置

以下数字均为建议初值。模型相关取值以选定服务实际支持为准。

| 配置项                                    | 建议初值            | 控制什么                                   |
| ----------------------------------------- | ------------------- | ------------------------------------------ |
| `runtime.backend`                         | `pi_core`           | 使用哪个执行实现                           |
| `model.provider`、`model.name`            | 部署时设置          | 模型服务和模型标识                         |
| `model.base_url`、`model.credentials_ref` | 部署时设置          | 服务入口和认证引用                         |
| `model.reasoning_level`                   | 按模型设置          | 模型推理强度                               |
| `model.max_output_tokens`                 | 按模型设置          | 每次模型响应的输出上限                     |
| `runtime.workspace_root`                  | 每个 agent 显式设置 | 文件与命令默认工作目录                     |
| `runtime.artifacts_root`                  | 部署时设置          | 生成文件与长期日志存放位置                 |
| `runtime.max_model_rounds`                | 50                  | 单次工作最多模型调用轮数，到限后记录并结束 |
| `runtime.request_timeout_seconds`         | 300                 | 单次模型请求等待上限                       |
| `runtime.tool_execution_mode`             | `sequential`        | 工具顺序执行或受控并行，先验证顺序执行     |
| `runtime.cancel_grace_seconds`            | 5                   | 本地执行进程收到取消后的清理等待时间       |
| `shell.default_timeout_seconds`           | 120                 | 普通命令的默认超时                         |
| `shell.max_timeout_seconds`               | 1800                | 单次命令可申请的超时上限                   |
| `skills.paths`                            | 显式配置列表        | 扫描哪些 Skills 目录                       |
| `mcp.servers`                             | 显式配置列表        | 服务名称、命令或地址、环境变量及认证引用   |
| `mcp.connect_timeout_seconds`             | 30                  | MCP 连接等待上限                           |
| `mcp.call_timeout_seconds`                | 120，可按服务覆盖   | MCP 单次调用等待上限                       |
| `tools.enabled`                           | 显式配置列表        | 本次可用的基础工具、网页工具和扩展工具     |

新消息打断和重启停止属于首版固定行为。记录展示长度和上下文预算见第4、5节；完整经历和附件随系统数据备份，保存期限由部署配置确定。

## 7. 四层联调验证顺序

1. Telegram 文字和附件进入第一层，封装后由第二层可靠保存；重复交付只形成一次有效入站事件。
2. 统一发送指令完成文字、图片和文件发送，支持输入状态及分段间隔，实际发送结果回到第二层。
3. 用简单的第三层提供上下文，让 Pi Core 读取附件、执行脚本、生成文件并交回发送。
4. 保存工具输入输出，启动一次全新的执行，借助我们提供的记录回答“刚才做了什么”。检查实际模型请求符合我们的上下文配置。
5. 接入一个常用 Skill 和一个 MCP 服务，验证发现、执行、结果返回及依赖准备。
6. 长任务期间发送新消息，验证取消、已有结果保存和下一次上下文；已交第一层的分段回复继续发完。
7. 重启程序，验证记录仍可使用、中断工作保持停止。检查发送失败、附件失败和服务断开均有明确反馈。

8. 验证工具记录、自身回复和发送回执只进入对应处理方向；同一内部事件反复投递只接手一次，沉默也能正常结束。
9. 验证定时和梦境分享事件沿统一入口进入第二、三、四层，保留真实来源并使用默认发送位置；执行期间到来的内部触发和用户消息采用同一打断流程。
10. 验证容量增长触发批量压缩、第三层按预算选择记忆、主动查询可分页，以及长工具循环中每次请求前的容量检查。记忆、情绪和表达效果按第5.13节检查。

11. 修改定时脚本并调用重启工具，确认仅重启脚本且单实例运行；固定时间取下一次匹配，随机间隔重新抽取，停机期间错过的时刻跳过。检查脚本提交失败和启动失败有可查看日志。

12. 验证先说话、调用工具、再说话的过程：中间文字及时入队，完整消息回传后不重发；第一层串行发送，取消后已提交块照常发送。
13. 验证附件先到消息、后到就绪或失败事件，其他收发照常；同批事件一起编排，重复就绪事件不重复触发。
14. 验证同一回复拆块和第一层分句不会被当作多条独立回复；第二层计算交流间隔并提供给state，第三层按配置渲染；跨渠道发送别名定位正确。

15. 验证直接沉默、只点表情后结束、只发附件后结束，均不自动补发一句话；工具失败与主动沉默分别记录。
16. 验证表情定位原消息，附件路径登记为稳定引用，平台能力不足返回明确结果；入队后取消不撤回动作，最终结束不重复发送。

17. 验证正常、沉默、取消、失败均只发出一次整轮结束回调；第二层结束记录不再次触发判断。平台发送延迟或失败不影响后台心情判断启动。
18. 验证同一次后台请求同时返回情绪变化和重温记忆编号，候选外编号被忽略，同一回调重复送达不重复应用；不同运行按各自材料判断，不增加跨轮情绪去重。

上述验证完成后，再依据实际结果确定依赖版本与实现细节。四层基本流程和算法已形成实施基线；群聊参与细则、具体定时脚本内容、部署方式和故障恢复细节在各自实现任务中细化。
